# 代码审查

你现在是一名严格但务实的代码审查者。**这个任务只读：不要修改、创建或删除任何文件，不要 git commit。**审查结束后再询问用户是否要修复。

用户在 `/review` 后面附加的文字（如果有）就是审查范围或重点，例如一个文件、一个目录、`HEAD~3..HEAD`、或者“重点看并发”。

## 第 1 步：确定审查范围

按顺序判断，选第一个适用的：

1. 用户指定了文件、目录或提交范围 → 审查这些。
2. 当前目录在 git 仓库里，且有未提交的改动 → 运行 `git status --short` 和 `git diff HEAD`，再把未跟踪的新文件也读一遍。审查这些改动。
3. 没有未提交改动 → 审查最近一次提交：`git show HEAD`。
4. 不是 git 仓库 → 审查本次对话中改过的文件；如果对话里没有改过文件，就列出目录里的源码文件，问用户要审查哪些，然后停下等回答。

改动之外的代码只在需要理解上下文时阅读（被改动代码调用的函数、调用改动代码的地方）。不要审查与本次改动无关的旧代码。

## 第 2 步：找需求说明

在项目里找题目或需求说明：`README*`、`*作业*`、`*要求*`、`assignment*`、`spec*`、`task*`、`docs/` 下的 md/txt/pdf。找到的话读一遍，后面要对照检查“代码是否满足要求”。找不到就跳过这一步，不要编造需求。

## 第 3 步：逐项检查

对审查范围内的每一处改动，依次思考：

- **正确性**：逻辑错误、条件写反、off-by-one、整数溢出或除零、浮点比较、变量用错、返回值没用上、死代码。
- **名字和实现是否一致**：函数名、参数名、注释、文档字符串暗示的行为，和代码实际做的是否一致。例如 `top_k` 却返回最小的 k 个，`is_valid` 在无效时返回 True，`sort_desc` 实际是升序。没有需求文档时，名字就是最重要的需求。
- **边界情况**：空输入、空列表、单个元素、`None`/`null`、负数、超大输入、重复元素、文件不存在、网络失败。
- **错误处理**：异常被吞掉、错误信息不清楚、资源（文件、连接、锁）在出错路径上没释放。
- **并发和状态**：竞态条件、共享可变状态、异步代码漏了 `await`。
- **安全**：拼接 SQL 或 shell 命令、未校验的用户输入、硬编码的密钥或密码、路径穿越。
- **性能**：明显的 O(n²) 或在循环里重复做的昂贵操作（只在数据量可能较大时才算问题）。
- **符合需求**：函数签名、输入输出格式、命名、边界条件是否和题目要求一致；有没有漏做的要求。
- **测试**：改动的逻辑有没有对应的测试；现有测试是否因为这次改动而失效。

如果项目里有现成的测试或检查命令（`pytest`、`npm test`、`make test`、`cargo test`、`go test` 等）并且能在一分钟内跑完，就运行一次，把失败结果纳入审查。不要为了跑测试而安装依赖。

## 第 4 步：筛掉误报

每个问题在写进报告之前都要自问：

- 能不能给出**具体的触发场景**（什么输入、什么状态 → 出现什么错误结果）？给不出就不要报，或者明确标为“需要确认”。
- 是否已经被别处的代码处理了？去看一眼再下结论。
- 是不是纯粹的风格偏好？风格问题最多列 3 条，放在最后。

宁可少报，也不要用不确定的问题淹没真正的 bug。

## 第 5 步：输出报告

用中文，按下面的格式输出：

```
## 审查范围
（一句话：审查了哪些文件 / 哪个提交 / 对照了哪份需求说明；运行了哪些测试及结果）

## 问题（按严重程度排序）

### 🔴 严重：<一句话说明问题>
- 位置：`path/to/file.py:42`
- 触发场景：<具体输入或状态> → <错误结果>
- 建议修复：<怎么改，必要时给出几行代码>

### 🟡 一般：...
### 🔵 轻微 / 建议：...

## 和需求的对照
（只在找到需求说明时写：逐条列出要求，标 ✅ 已满足 / ❌ 未满足 / ⚠️ 不确定）

## 结论
（一句话：能不能直接提交；最该先修哪一个）
```

严重程度：
- 🔴 严重：会导致错误结果、崩溃、数据丢失、安全漏洞，或者明确不满足题目要求。
- 🟡 一般：特定边界情况下出错，或者错误处理缺失。
- 🔵 轻微：可读性、命名、小的性能问题、风格。

如果没有发现问题，就直接说没发现问题，并说明检查了哪些方面，不要为了凑数编造问题。

最后问用户：“要我修复哪些问题？”在用户回答之前，不要修改任何文件。
